3设计决策

3.1 head 聚合语义

MSA 的打分器以 MQA proxy-Q 模式工作，每个 KV head 一行分数。三种 head 模式的输入 因此完全相同，区别只在于对这 Hkv 行做什么：

head_mode打分器行数选择份数含义
keepHkv = 44 分数原样使用，每个 KV head 一份自己的选择。这是 MSA 的出厂行为。
sumHkv = 41 把 4 行求和，整层共享一份选择：被各 KV head 普遍需要的块胜出。
maxHkv = 41 同上取 max：只要任一 KV head 想要就保留，跨 head 尺度无关。

所以 sum/max 比 keep 便宜——打分器工作量完全相同， 而 top-k 只需产出 1 行而不是 4 行。单份选择再广播回 Hkv 交给 CSR （其元数据以 KV head 为键，且要求连续张量，所以 expand 不够，需要一次 contiguous()）。

这里我走过一次弯路，值得记下来

第一版把 sum/max 实现成了「对 32 个 query head 的分数归约」 ——那需要打分器先算 32 行，归约发生在昂贵那级的下游，结果 sum/max 比 keep 慢 4×， 128K 时还会撞上 §8.2 的 Int32 上限跑不了。那个结论是实现假设的产物，不是这两个模式的性质。 按上表的正确语义重测后，sum/max 反而比 keep 快 1.08–1.27×。 §7b 给出修正后的对比；§7 的 12 组主矩阵已按正确语义重跑。

3.2 force 窗口以 token 表达

force_init/force_end 用 token 计（128），在配置层向上取整换算成块， 使同一份配置在 block 变化时保持语义不变：block=32 → 4 块，block=64 → 2 块。两个窗口 占用 topk 预算而非叠加，因此 force_init_blocks + force_end_blocks ≤ topk 是配置层的硬校验。

3.3 force_end 的因果锚点

原实现把 local 窗口锚在 num_valid_pages（序列末尾），这对 decode 正确 （query 就在序列末尾），对 prefill 则不是滑动窗口。新增可选的 causal_end_block[total_q]：逐 query 传入其因果块上界，local 窗口锚在 每个 query 自己的位置。不传时退化为原行为，向后兼容。

3.4 融合而非新增 pass

head 聚合、force 窗口标记、输出布局三件事全部折进 top-k 的 transpose 阶段—— 那是唯一一个本来就要完整流过分数张量的 kernel。这样三个特性都不引入额外的全张量访存。

4.1 环境搭建

4.2 top-k 选择内核：可配置化

文件：python/fmha_sm100/csrc/include/sparse_topk_select.cuh、 csrc/sparse_topk_select.cu、api.py

  • 运行时 topk：SparseTopKSelect 的 constexpr topk = 16 改为参数， 按运行时值选择 IndexerTopKWithSortKernel<16|32|64> 模板桶。 模板与 WarpBitonicSortAsc32/64 原本就已备好，此前只是没有派发路径。
  • head 聚合：transpose kernel 模板化为 kHeadReduceNone/Sum/Max，读入 group_size 个 head 行在寄存器里归约后 再写转置结果。float4 XOR-swizzle 快速路径同样支持，每个 group 成员一次 float4 读， SMEM 流量不变。
  • 逐 query 因果 force 窗口：新增可选 causal_end_block，force 判定改为 SparseTopKIsForced(k, q_end, force_begin, force_end_blocks)； 用 k + force_end >= q_end 写法避免无符号下溢。
  • head-outermost 输出：新增 head_outermost 开关，直接写出 [Hkv, total_q, topk]——正是 build_k2q_csr 需要的布局， 省掉生产路径上一次全量 permute+copy。

4.3 JIT 缓存按源码内容失效

文件：python/fmha_sm100/jit.py

_do_compile_sparse_topk() 原本只要 .so 存在就直接返回，而 sparse_topk_select.cuh 是通过 -I 从源码树读的、并不拷进缓存目录—— 改内核不会触发重编译，会静默用旧 kernel。改为对 .cu + .cuh + tvm_ffi_utils.h 做 SHA-256 指纹并落 stamp 文件，指纹变化即重编； 编译前先删 stamp，避免编译中断留下「新指纹 + 旧 .so」。用内容而非 mtime，因为 editable 安装、git checkout、容器 bind-mount 都会无意义地改动 mtime。

4.4 CSR builder 支持 blk_kv 32 / 64

文件：cute/src/sm100/build_k2q_csr/build_k2q_csr.cu、 cute/src/sm100/prepare_k2q_csr.py

核查后确认 kBlockK 模板参数在整个 pipeline 中只用于 ceil(seqlen_k / kBlockK) 的行数运算（k2q_build_row_map_kernel）， 其余 kernel 只是透传。因此 32/64 是精确而非近似支持。把 TORCH_CHECK(blk_kv == 128) 换成 {32,64,128} 校验，并用宏把 (topK × blk_kv) 的 12 个实例化展开，两个入口共用。

4.5 容器内 CUDA 构建修复（两处）

文件：cute/src/sm100/build_k2q_csr/__init__.py

  • cusparse.h: No such file：容器用 pip CUDA stack， cusparse.h 在 site-packages/nvidia/cu13/include 而不在 /usr/local/cuda/include，而 ATen/cuda/CUDAContext.h 需要它。 直接把 wheel 的 include 目录整个加进去会反向踩雷： extra_include_paths 排在 -isystem $CUDA_HOME/include 之前， wheel 里的 crt/host_runtime.h 会遮蔽 nvcc 自带版本，导致 macro "__cudaLaunch" passed 2 arguments。最终做法：建一个 shim 目录， 只软链 CUDA_HOME 缺失的头文件，绝不遮蔽已有的。
  • __cudaLaunch was not declared：CUDA 12.8 把 -static-global-template-stub 默认翻成 true，与匿名 namespace 里的 模板 __global__ 冲突。仓库自己的 csrc JIT 早就固定了这个 flag， 这里按 torch.version.cuda ≥ 12.8 条件补上。同时把 -arch=sm_100 改为按实际设备能力取（B300 上是 sm_103）， 省掉每次进程启动的 PTX JIT。

4.6 配置层与流水线

新增 python/fmha_sm100/msa_config.py（无 CUDA 依赖，任意机器可导入）： MsaSparseConfig 数据类 + 校验 + 三种字符串格式互转 （slug fi128-fe128-b32-k16-hkeep / label force_init(128)-... / key=value 列表）+ 环境变量读取 + 12 组矩阵 + MODEL_N16 模型形状。

4.7 benchmark 暴露的 indexer host 瓶颈（当场修复）

文件：cute/fp4_indexer_interface.py

第一版 benchmark 跑出来 indexer 的 eager 延迟是 8K 下 1.13 ms、32K 下 15.7 ms， 而且 2 head 和 16 head 完全一样——GPU 计算量差 8× 时间却不变，说明瓶颈在 host 而非 kernel。 定位到 _causal_compact_task_bound 是 O(q_tiles²) 的纯 Python 双重循环， 且每次调用重算。加 lru_cache 后 32K 从 15.66 ms 降到 0.254 ms（61.6×）。 细节与后续建议见 §8.1。

5.4 选择质量验证 —— head 模式的 keep / sum / max

§7 的 benchmark 只回答了「哪个配置快」。head_mode 本质是质量/成本的权衡， 只按延迟排序不构成答案。这一组补上质量的一半，用的是真实训练权重的 Q/K而不是随机张量： 从 model-n32 checkpoint <checkpoint>（Hq=32 / Hkv=4 / GQA 8 / D=128，与目标完全一致） 直接读单层的 q_proj / k_proj / q_layernorm / k_layernorm，复现 qk-layernorm → RoPE， 算出精确的 dense attention，再问每种选择保住了多少注意力概率质量。

指标

对 query q、query head h，dense 权重 p(q,·)、选中 token 集 S(q,h)：recall(q,h) = Σ_{j∈S} p(q,j)。 这是 NSA / MoBA / DSA 都在用的标准量，等于稀疏内核还能看到的 softmax 分子占比。 除均值外两个统计量更关键：p5（5 分位，尾部有多差）与 min-in-group（GQA 组内被服务得最差的那个 query head——共享选择的下限就在这里）。

模式含义
oracle每个 query head 各选各的 top-k。内核做不到（CSR 元数据以 KV head 为键）， 但它是任何共享方案的上界，让「sum vs max」有了标尺
sum / max把 keep 的同一批 Hkv=4 行 proxy 分数归约成 一份整层共享的选择——打分器工作量与 keep 完全相同
keep每个 KV head 一行分数。MSA 期望它来自单独的 proxy-Q 投影，而 MSA 并不训练这个投影， 这里用组内 Q 向量池化顶替（池化必须发生在 QK 之前——对分数池化只等价于 sum 乘一个正常数， top-k 不变）。所以 keep 这一行是下界：真正训练过的 proxy 只会更好

结论
  1. 排序稳定：keep > sum > max，4 个 (seqlen, 形状) 组合、三个统计量无一例外。 质量与共享程度直接挂钩：4 份选择 > 1 份选择。
  2. max 应当排除。它和 sum 成本一样（实测差 <1%）， 质量却始终差 3.2–4.2 个点——被严格支配。
  3. keep 与 sum 是一个真实的取舍： sum 快 1.08–1.27×（§7b），质量差 1.4–2.9 个点。 短上下文（≤32K）sum 的速度优势最大而质量差距也最大； 长上下文（≥64K）速度优势缩到 1.08–1.14×，此时 keep 的质量更划算。
  4. 预算压倒 head 模式。16K 下把 topk 从 16 提到 32， sum 的 recall 从 0.871 涨到 0.894，超过 keep@topk=16 的 0.900 附近——加预算比换模式更有效。

decode 走不通，而且是两个独立原因
  1. CSR builder 的 SMEM 直方图随 total_rows = batch × ⌈S/block⌉ 爆掉。 根因定位到 build_k2q_csr.cu 的降级循环本身： 
    int per_warp_smem = ((total_rows + 1) >> 1) * sizeof(int);   // = total_rows × 2 字节
int kWarps_pick = 4;
while (kWarps_pick > 1 && (kWarps_pick * per_warp_smem) * 2 > 228*1024) {
    kWarps_pick >>= 1;                    // 只降到 1 就停
}
    kWarps_pick 降到 1 后循环退出，但从不检查单个 warp 的直方图是否还放得下， 于是 cudaFuncSetAttribute 失败，向上只表现为一句 CUDA error: invalid argument。精确边界是 total_rows × 2 B ≤ 227 KB，即 total_rows ≤ 116,224。 实测卡在这条线上：512K/blk128 时 B=28（114,688 行）跑通、B=32（131,072 行）失败。 prefill 因为 batch=1、total_rows 只有 ⌈S/block⌉，从未暴露过这个限制。 现已在 prepare_k2q_csr.py 加了前置检查，报出具体行数、上限和绕行办法， 不再退化成 CUDA 通用错误。
  2. blk=32 在 ≥512K 撞的是另一条限制，不是同一个。 sparse_topk_select 只实现了插入排序路径，要求 max_k_tiles = ⌈kv_len / block⌉ < 12288（radix-sort 路径未实现）。 按 block 换算可达上下文为 blk32/64/128 → 393K / 786K / 1.5M token。 两条限制叠加后，B=32 decode 的可行域是：32K 全通、128K 仅 blk≥64、 512K 与 1M 全部不可达。
  3. 稀疏注意力在 decode 下拿不到收益。128K/baseline 只选 2048/131072 ≈ 1.6% 的 token， 理论该快 60 倍，实测 attention 阶段 1.17 ms vs dense 1.21 ms——几乎没省。 原因是 prefill 内核 m_block_size=128 打包 Q-head，qhead_per_kv=8 时 一个 tile 只有 16 个 query token；B=32 总共 2 个 tile，SM 大量闲置。

MSA 为此备了专用的 sparse_decode_atten_func，但它硬性要求 qhead_per_kv=16 且 page_size=128——model-n32 是 8，用不了。 所以结论不是「decode 收益小」，而是这个模型走不到那条 decode 内核上。

512K 那一列的 dense 分母作废

重跑全网格后发现，dense 参照组在 512K prefill 会非法访存。 total_qo_len × num_qo_heads × head_dim = 524288 × 32 × 128 = 2,147,483,648， 正好等于 2³¹——和 §8 里 indexer 那条 Int32 守卫是同一类问题，只是这次在 dense/attention 路径上，原本没有守卫。实测边界：262144 与 458752 正常，524288 每次都崩。

最坏的性质是它不总是崩。完整 run 里 dense@512K 报出 1739.684 ms 并写进了表格， 而同一 shape 在干净进程里三次全崩（真实 Q/K 与随机 Q/K 都一样）。区别只在分配器状态， 这正是 2³¹ 边界问题的典型表现：是否触发取决于基址而非数值。 所以上面各表 512K 那一列的分母不可信，应当作废。

已在 fmha_sm100() 入口按 q.shape 加守卫，把非法访存换成带诊断的 ValueError。验证后 512K 干净报错且 CUDA context 存活—— 之前一个坏 shape 会污染 context、带走整场扫描的后续全部配置。

7eKV-outer 后端对比（fireworks-msa 分支）

MiniMax-AI/MSA 的 fireworks-msa 分支加了一个约 6000 行的 kvouter 模块，用 KV-stationary 循环 + LSE merge 替换掉当前的 build_k2q_csr + Q-outer forward。这正对着 §8 里那条最大的结构性问题： 当前实现的 O_partial = empty(topK, total_q, head_q, dim) 让 partial-O 流量 ∝ topk，而不是 ∝ 实际访问的 token 数。

对比口径
  • 两侧用同一份 selected、同一份 Q/K/V（两个 checkout 都提供 fmha_sm100 包，无法同进程导入，所以走两段式：双方用相同种子逐位重建 Q/K/V，只把 selection 和输出落盘交换）。
  • 只比 stage 3–4。FP4 indexer 与 top-k select 两侧完全相同，不计入任何一边。
  • KV-outer 有 assert block_size == 128 and head_dim == 128， 所以对比只在 block=128 上成立——正好是 §7c 推荐配置所在的那一列。
  • KV-outer 吃分页 KV cache，当前实现吃扁平 KV；打包是 setup，不计时。
  • 跑的是 Python CuTe-DSL 后端，因为容器里 cpp_backend_available() 为 False。分支自己把 AOT C++ 路径列为优先、Python 为 fallback， 所以下表低估了分支的真实水平，小 shape 上尤甚。

结论：优势沿对角线出现，且和推荐配置错位
  1. KV-outer 赢在长上下文 + 大 topk。32K 要 topk≥32 才追平，256K 从 topk=4 就领先，最高 1.15×。交叉线大致是一条对角线：上下文每翻一倍，追平所需的 topk 减半。
  2. 短上下文 + 小 topk 反而慢，最差 0.67×。KV-outer 的 index build 与 LSE merge 是固定开销，小规模摊不掉——而这部分很可能就是 Python fallback 的 dispatch 开销， C++ 路径下未必成立。
  3. 和 §7c 的推荐配置错位。本仓库的扫描结论是「往大 block、小 topk 走」 （cfg24 = blk128/topk8）。而 KV-outer 恰恰在大 topk 上收益最大， 在 topk=8 这一列只有 1.03×（128K）到 1.12×（256K）。 换句话说：它没有改变最优配置的位置，只是把远离最优点那一侧的惩罚变轻了。
  4. topk 的伸缩性确实改善了，但没有质变。topk 从 4 涨到 32（8× 的 KV 读取量）， q-outer 耗时涨 4.5–5.5×，KV-outer 涨 3.0–5.0×。两者都低于 8×，说明小 topk 侧 都是被固定开销主导的；KV-outer 只是把 topk 相关的那部分斜率压低， 并没有把 partial-O 的代价完全消掉。

因此这条分支值得合，但它不是 §8 里 #1 优先级的答案。 在推荐工作点（blk128/topk8）上它带来 1.03–1.12×，而同一位置 indexer 占了 长上下文下流水线的 72%——收益量级差一个数量级。真正的顺序仍是： 先修 indexer 的超二次增长，再考虑换 forward。

  3. b15 自身也用 cute.core.ThrMma，整条依赖链锁死在 cutlass-dsl 4.5.x。

8.2 已加守卫 indexer 分数张量的 Int32 寻址上限

这是本轮 benchmark 撞出来的一个真 bug。128K + head=sum 直接 CUDA error: an illegal memory access，而且会污染整个 CUDA context， 导致后续所有配置连带失败。

根因：fp4_indexer_interface.py 把分数张量的 CuTe layout 用 Int32(...) 构造，kernel 内部因此以 32 位有符号算术计算线性偏移， 可寻址的最后一个元素是 231−1。分数张量的元素数是 scorer_heads × ceil(S/128) × total_q：

head_modescorer heads S=32KS=64KS=128KS=256K 可跑的最大 S
keep4 (=Hkv) 0.034e90.134e90.537e9 2.147e9
（正好 =231）		262,144
sum / max32 (=Hq) 0.268e91.074e9 4.295e9 溢出 17.18e9 溢出 92,672

也就是说 keep 恰好能撑到 256K（一个巧合般的边界）， 而 sum/max 在 92,672 token 就断了。 本轮已在 fp4_indexer_block_scores 入口加了显式校验， 把「静默内存踩踏」换成一条带诊断的 ValueError：

ValueError: FP4 indexer score tensor would need 4294967296 elements
(Hq=32 x k_tiles=1024 x total_q=131072), above the Int32-addressable limit of
2147483648. Reduce the scorer head count (e.g. per-KV-head scoring instead of
per-query-head), split the batch, or chunk the prefill.

MsaSparseAttention.max_scorer_seqlen() 把同一个上界暴露给调用方做容量规划。 根治要么把 layout 换成 Int64 extent，要么按 §8.5 把 GQA 归约下沉到 indexer—— 后者顺带把 sum/max 的分数张量降 8×，上限直接推到和 keep 一样。

这条也改变了 §7 的读法

128K 下 cfg05–cfg12 的 indexer 跑不了，但 top-k / CSR / attention 三级仍能测。 把跑得通的几级加起来当总耗时是错的——那等于把跑不通的那部分当成免费的， 会得出「sum/max 在 128K 最快」这种完全反的结论。§7 的表格已把这些行排除在排名之外并单独标注。

8.3 已修复 indexer 的 O(q_tiles²) host 循环

现象：fp4_indexer_block_scores 的 eager 延迟远高于 GPU 时间， 且与 head 数无关——2 head 和 16 head 都是同一个数，而 GPU 计算量差 8×。

根因在 _causal_compact_task_bound：它枚举 q_tile_count 个候选 q 长度， 每个候选再调 _causal_compact_task_count 循环 q_tile_count 次—— 整体 O(q_tiles²) 的纯 Python，且在每一次 indexer 调用时重算。 它只是给 kernel 算一个 grid 上界，与张量内容毫无关系。

cfg02 与 cfg03 访问的 KV token 数完全相同（1024），耗时却差 1.8×。 更直接的证据在最后一列：cfg01 只访问 512 token，cfg03 访问 1024 token， 两者 topk 都是 16——耗时几乎一样。 耗时跟 topk 走，不跟 token 数走。

根因在 cute/interface.py::_sparse_atten_csr_varlen_forward：

O_partial   = torch.empty(topK, total_q, head_q, dim, dtype=partial_dtype, ...)
LSE_partial = torch.empty(topK, total_q, head_q, dtype=torch.float32, ...)

一个 CTA 处理 m_block_size=128 个 packed Q-head（qhead_per_kv=8 时即 16 个 query token）× 1 个 KV block，每个 tile 写出一条 partial O，最后由 combine 归约。partial 的写出量因此是 topk × total_q × Hq × D，与 block_size 无关：

32K164.29 GB8.6 GB
32K328.59 GB17.2 GB
128K3234.36 GB68.7 GB

副作用是 block 越小，epilogue 与计算的比值越差：CTA 的 MMA 工作量是 128 × block_size × 128，而 partial 写出恒为 128 × 128， 所以 block=32 的单位计算 epilogue 开销是 block=128 的 4 倍。这正是 12 组配置里 小 block 没能换来收益的原因。

建议（按代价从低到高）：

  1. 每个 split 吃 G 个 KV block（G>1）。选择结果本来就按块索引升序，CTA 可以连续 处理 G 个块、在 TMEM 里用 online-softmax 累加，只写一条 partial，流量降为 topk/G。 block=32 取 G=4 就能把 epilogue 比恢复到 block=128 的水平。收益最大且与现有 CSR/schedule 兼容。
  2. partial dtype 降到 fp8。partial_dtype 已是参数（支持 fp8_e4m3），流量直接减半。
  3. partial 槽位数跟随 schedule 实际 split 数而非 topK 上界； split_counts 已经算出来了，目前只用于 combine，没用来收缩分配。

8.5 建议 三件事落在同一处 indexer epilogue，建议合并做

  • GQA 归约下沉（收益最大）：sum/max 现在要写出 Hq=32 行分数、 top-k 再读回来归约。在 indexer 的 CTA 内先把同组 8 个 head 归约掉， 分数张量、写带宽、top-k 读入、workspace 全部降 8×，并且 §8.2 的 Int32 上限 从 92,672 直接推到和 keep 一样的 262,144。无法避免的只有 QK 的 MMA 量。 64K 下 sum 的选择级现在是 40.4 ms（keep 只要 5.1 ms），这一项做完应大幅回落。
  • 子块粒度：现在 epilogue 对整个 128 列 N tile 做一次 row-max。 改成 128/block_size 个子块累加器即可原生支持 block=32/64。 B300 走的是 tcgen05.LdRed32x32bOp(Repetition.x128, ..., MAX) 的硬件整行归约， 改成按列区间发 Repetition.x32 四次就能拿到 32 粒度。
    注意：本轮 benchmark 中 block=32/64 的 top-k / CSR / attention 三级都是真实精确的， 唯独打分级仍产出 128 粒度分数（其 MMA 量与 block 无关，只有写出量会变），这是唯一的测量偏差。
  • 直接写转置布局：sparse_topk_select 的第一级要把 [H, K, qo] 转成 [H, qo, K] 存进 workspace——128K/block32/keep 时是 8.6 GB 的额外一读一写。indexer 的 epilogue 本来就是逐 (q, ktile) 标量写， 直接写成转置布局即可整个省掉 transpose kernel（需评估写合并度）。

8.7 配置选择结论

  1. 推荐生产配置：force_init(128)-force_end(128)-block(64)-topk(16)-head(sum)（cfg07）。 全部 8 个上下文点上都是最快或并列最快：16K 1.03×、32K 2.12×、64K 2.73×、128K 2.39× dense。 交叉点 ~15.9K，比 keep 系的 ~20.5K 早了近 5K token。
  2. 若质量优先则选 cfg03（head=keep）。 keep 给每个 KV head 一份选择，recall 比 sum 高 1.4–2.9 个点（§5.4）， 代价是慢 1.08–1.27×、交叉点晚到 ~20.5K。 ≥64K 时 sum 的速度优势只剩 1.08–1.14×，此时 keep 的质量更划算。
  3. max 排除。与 sum 速度差 <2%（cfg11 vs cfg07 全程在 1% 内）， 质量却始终差 3.2–4.2 个点——严格被支配。
  4. topk=16 全面优于 topk=32。 cfg07 (k16) vs cfg08 (k32) 在 128K 是 2.39× vs 2.05×。耗时跟 topk 走而不跟 token 预算走（§8.4）， 所以同预算下永远选大 block / 小 topk。
  5. 交叉点 ~15.9K–20.5K，取决于 head 模式。模型当前的 4096 训练上下文远在其下—— 4K 时最好的配置也只有 0.26×，×46 层每前向多花 13.4 ms。 MSA 对这个模型的价值在长上下文推理，不在 4K 训练配置。
  6. 优势在 64K 见顶随后回落（cfg07 2.73× → 2.39×）。吃掉这部分的是 §8.1 的 indexer 超二次增长。
测量口径

机器上其它容器在跑，dense 参照组的 run-to-run 波动约 ±8%（16K 下 1.38–1.48 ms）。 接近 1.0× 的格子应读作「约等于」，不要用来区分 0.97× 和 1.03×。 ≥32K 的比值波动在 2% 以内，结论稳定。
